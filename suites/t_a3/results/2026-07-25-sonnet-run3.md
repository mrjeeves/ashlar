# A3 gate — run 3

**Model under test:** `claude-sonnet-5` (readers), `claude-opus-5` (judges)
**Date:** 2026-07-25
**Corpus:** 25 snippets (`25-foreign-reactive` added for this run)
**Result: 23 / 25 PASS — corpus PASSES** the 80% bar (20 of 25).

Run 2 (2026-07-22) scored 23/24 against a 24-snippet corpus. Since then the
language gained two constructs: `owned` (ADR-0015) and the `reads`/`writes`
foreign annotation (ADR-0014's reactive stage). **Both fail this run**, and
nothing else that failed. The corpus still clears the bar, so A3 is satisfied
as a requirement — but the gate has done exactly the job it exists for, and
the two findings are design bugs in the syntax, not documentation gaps.

## Method

Run faithfully per `PROTOCOL.md`, with two deliberate strengthenings, both
recorded here because they affect how the numbers should be read:

1. **The cold read is provably cold.** Each reader was a fresh agent given the
   snippet text *inline* and explicitly forbidden from reading, listing,
   grepping, or searching any file. It could not reach `reference/ashlar.md`
   even accidentally. One snippet per reader, no shared context between
   snippets.
2. **Failures were adversarially re-judged.** A single judge decides each
   snippet, as the protocol specifies. But a FAIL is a claim that syntax
   should be redesigned, so every failure went to two further independent
   judges — one instructed to lean charitable, one to lean strict — and the
   majority of the three decided. This changed one outcome: `03-layering`
   was failed by the first judge and passed by both others, so it is recorded
   PASS. Neither failure below survived on a single judge's opinion; both are
   unanimous 3/3.

56 agent runs in total.

## Finding A3-F5 — `owned` reads as encapsulation, not as per-user scope

**`11-owned`, FAIL, 3/4 bullets + wrong-claim flag, unanimous 3/3.**

The reader took `owned` to mean *this part holds its own private state*:

> "`owned` indicates the field is state that `Store` itself holds and manages
> (as opposed to a reference/prop passed in from outside)"

…and concluded the snippet declares "a minimal data store that keeps a
mutable, growable list of strings which survives across runs" — one shared
list. The per-user meaning, which is the entire point of the modifier, did not
appear. Every other fact was read correctly: `stored` persists, the shape is a
list of text, the default is empty.

This matters more than a missed bullet, because the misread is **silently
wrong in the direction of a security bug**. `owned` exists so that per-user
isolation is the naive reading (ADR-0015: "the naive read is the safe read").
A reader who thinks `owned` means encapsulation will believe a shared store is
per-user, or write code assuming one list where there are many.

**The meta-finding is about how the word was chosen.** ADR-0015 justified
`owned` with a cold read that scored `owned`/`personal`/`user` per-user 3/3,
and rejected `private` because it "misread as OOP access-control." That test
asked what the *word* suggests. This test shows what the *construct* does to a
reader — and in `owned stored items`, `owned` lands in exactly the OOP/Rust
ownership frame that `private` was rejected for. A word-level cold read is not
a substitute for a construct-level one, and A3 is defined over constructs.

## Finding A3-F6 — `reads`/`writes` read as an effect annotation, not a reactive edge

**`25-foreign-reactive`, FAIL, 2/4 bullets, unanimous 3/3.** The worst score
in the corpus.

The reader took the annotations for static effect documentation — "only reads
Row state (no mutation)", "the effect it has on program state is declared
right in the signature rather than left implicit." Reactivity was **entirely
absent**: no mention of views, re-rendering, propagation, or clients.

That is a plausible, useful-sounding, and wrong mental model, which is the
A4 failure mode named in the requirements: false familiarity is worse than
unfamiliarity. `reads`/`writes` resemble an effect system, so a reader stops
at effects. The consequence for an author is not a compile error — it is not
understanding why a page updated, or declaring `reads` and expecting nothing
to happen.

## Verbatim failing answers

The protocol requires these so a syntax fix can be judged against the actual
wrong reading rather than a summary of it.

### `11-owned`

```
**Line by line**

- `space notes.data` — a namespace/module declaration. Everything that follows in the file belongs to the dotted namespace `notes.data` (a `data` sub‑module of a `notes` module/app), the way `package`/`module` statements scope a file in other languages.

- `part Store { ... }` — declares a named unit called `Store` using the `part` keyword. A "part" is this language's unit of reusable, named declaration (the kind of thing that gets instantiated/composed elsewhere and whose name must be unique/non‑colliding in scope). Here it's being used as a data-holding part — effectively a small data model/store named `Store`, not necessarily a visual component.

- `owned stored items: [text] = []` — a single field declaration inside `Store`:
  - `items` is the field's name.
  - `: [text]` is its type: a list/array of `text` values (`text` being the language's string-like primitive type).
  - `= []` is the field's default/initial value: an empty list.
  - `owned` and `stored` are modifiers on the field. `owned` indicates the field is state that `Store` itself holds and manages (as opposed to a reference/prop passed in from outside). `stored` indicates the field is persisted — its value is written to and reloaded from durable state rather than existing only transiently in memory.

**What it does overall**

It declares, in the `notes.data` namespace, a part named `Store` with one piece of persistent, self-owned state: a list of text strings called `items`, defaulting to empty. In effect this is the declaration of a simple persisted list of text items (e.g., notes) — a minimal data store that keeps a mutable, growable list of strings which survives across runs of the program, starting out empty until items are added to it.
```

### `25-foreign-reactive`

```
This snippet declares a namespace and a small persistence interface built on foreign (externally-implemented) functions.

- `space store` — opens/declares a namespace called `store` that the following declarations belong to.
- `part Row { key: text }` — defines a data type (record/shape) named `Row` with a single field `key` of type `text`.
- `foreign save: (key: text) -> bool writes Row` — declares a function named `save`, implemented outside this language (a foreign/native binding rather than a body written in this language), taking one parameter `key` of type `text` and returning a `bool` (presumably indicating success/failure of the save). The trailing `writes Row` is an effect annotation stating that calling `save` mutates/persists state associated with the `Row` type — i.e., it's declared as a side-effecting operation that writes a `Row` record (keyed, plausibly, by `key`).
- `foreign all: () -> [Row] reads Row` — declares another foreign function `all`, taking no parameters and returning a list/array of `Row` (`[Row]`). Its `reads Row` annotation declares that it only reads Row state (no mutation), consistent with "return every stored Row."

Taken together, the snippet is the interface layer for a simple key-value/row store: a `Row` shape with a `key` field, plus two externally-implemented operations — `save` (write one row, report success as a bool) and `all` (read back every row) — each carrying an explicit effect annotation (`writes`/`reads`) tying the operation to the specific data type (`Row`) it touches, so the effect it has on program state is declared right in the signature rather than left implicit.
```
